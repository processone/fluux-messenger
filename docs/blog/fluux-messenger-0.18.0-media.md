## Demo content and proof boundaries

All contacts, conversations, attachments and encryption identities are the
project's existing isolated demo data. The dedicated desktop scene injects
sample messages through `DemoClient`, then opens the room through the UI. It
asserts the unread avatar badge, absence of a mention badge, numbered divider
and final message before capturing. Its sidebar is widened through the actual
resize handle so names remain readable beside the avatar count.

The iPhone images come from this checkout's unsigned **Fluux iOS Demo**
(`net.processone.fluux.demo`) on an iPhone 17 Pro simulator running iOS 27.0,
built with Xcode 27.1. They are not mobile-browser images or connected accounts.
A simulator screenshot demonstrates the native interface, not working push,
Siri, system sharing, encryption interoperability or real-device qualification.
The native demo's scripted messages can change list order; inspect the current
frame before selecting a conversation. The final chat capture waits for the
floating date label to disappear and keeps the keyboard closed.

The reel reuses the existing director, storyboard, Aurora logo, bundled fonts,
avatars and attachment samples. It refreshes the application frames, rather than
splicing older footage into a new title. Its introduction reads 0.18.0 from the
root `package.json`. The scene order is unchanged:

1. Branded introduction.
2. Direct messaging, composing, typing, incoming reply and reaction.
3. Room replies and syntax-highlighted code.
4. File and image sharing.
5. Edit and unsend.
6. Command palette navigation.
7. Group rooms, members and presence.
8. OpenPGP demo conversation and trust display.
9. Light, Nord, Dracula and Aurora dark themes.
10. Branded closing.

This is a refreshed general product walkthrough, not a demonstration of every
0.18.0 fix or native iOS feature. The full-tour variant was not regenerated.

## Reproduction

Only one heavy job may run on the Mac. Coordinate the slot before a native
build, simulator or render; run the following phases sequentially. Do not use
personal signing material or connected accounts.

1. Install the locked dependencies and run `npm run build:sdk` with a supported
   Node version. This capture used Node 22 for builds and capture commands.
2. Run `npm run screenshots -- --workers=1` for the desktop gallery, including
   the release scene. That scene can be selected with `--grep '33 —'`.
   Encryption settings capture opens **Key details** before checking the demo
   fingerprint, because that disclosure is now collapsed by default.
3. Following [iOS development](../IOS_DEVELOPMENT.md), initialize this checkout
   with `npm run tauri:ios:init`, then run
   `npm run tauri:ios:demo -- "SIMULATOR_NAME_OR_UDID"`. Use the unsigned simulator
   path, not a device/signing build. Generate the Xcode project in this checkout;
   never copy another checkout's generated project. Build preparation can run
   under a scratch HOME, keeping signing storage isolated.
4. Wait for a rendered first screen before capturing. Direct simulator framebuffer
   capture works independently of desktop screen capture; if the resulting frame
   is black, stop rather than repeatedly capturing a locked session. Set a
   consistent simulator status bar (9:41, full battery and signal), capture the
   list, open Emma's conversation, wait for transient overlays to clear, and
   capture the chat. Stop the simulator before the next heavy phase.
5. Render only the new hero with `node scripts/blog-hero/render.mjs 0.18.0`.
6. Set `FLUUX_VIDEO_OUTPUT_DIR` to an absolute temporary directory outside the
   checkout and run `npm run demo:video:reel`. Re-encode its MP4 into
   `assets/readme/fluux-demo.mp4` using the `demo:video:readme` encoding settings
   in the root `package.json`, substituting the custom input directory.

The recorder produces native 1080p frames without upscaling. Keep its bulk frames
and master MP4/WebM exports outside the checkout; commit only the compact reel.
Inspect the gallery images, the thumbnail at its intended display size, and
samples across every video scene and transition. Record actual output metadata
with `ffprobe`, rather than relying on old approximate durations. Keep inspection
images, excerpts, transcripts and logs outside the project.

For validation, run the local selector's `--list` against the final branch and
its selected checks, including type checking for capture sources. No application
or native implementation changes are needed for these assets. The accepted blog
prose and its publication-date placeholder remain unchanged.
